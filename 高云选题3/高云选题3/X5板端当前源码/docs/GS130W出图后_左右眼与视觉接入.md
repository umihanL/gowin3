## 1. 哪个需要一直运行

`source /opt/tros/humble/setup.bash`只是给当前终端设置ROS软件路径，执行后立即结束，每个新终端按需执行一次。

`bash .../run_cam.sh ...`启动真正采集相机的程序。要持续获得新图像，采集节点必须一直运行。当前采集与官方原图预览在用户的终端前台运行，按Ctrl+C会停止对应程序，关SSH终端也可能使程序退出；YOLO与8086检测网页目前由两项临时服务管理，见第8节。浏览器只是显示图像，关闭浏览器通常不影响采集。

整个小车将来可以由一个ROS launch配合systemd服务自动启动采集、识别和任务程序，不需要手动守着多个终端。本次新入口复用已经运行的官方相机；没有设置整车开机自启。

**相机只由一个驱动进程占用。** `run_cam.sh`本身采集相机；官方`mipi_cam_dual_channel_websocket.launch.py`也包含相机启动，不能认为它只打开网页。已经启动采集时，网页应使用本工程的`tools/run_mipi_preview.sh`，只启动JPEG编码和websocket，订阅现有图像，不再打开第二套相机驱动。

## 3. 你已经确认左右顺序反了

左右以**站在相机后方、朝拍摄方向看**为准。在相机前面对镜头时，人的左右会反过来。

你已反馈：遮住物理左镜头，网页**下半幅变暗**。当前官方合成图上半为`/image_left_raw`、下半为`/image_right_raw`，因此当前映射是：

| 实际镜头 | 当前官方话题 | 当前网页 |
|---|---|---|
| 物理左眼 | `/image_right_raw` | 下半幅 |
| 物理右眼 | `/image_left_raw` | 上半幅 |

算法入口默认`swap_eyes=true`，在桥接节点内交换图像，因此送入YOLO的左图是**实际物理左眼**。8000官方双目网页仍按原顺序显示；8086新网页显示算法使用的单个物理左眼画面及检测框。再次遮住物理右眼，8000网页应看到上半幅变暗，可交叉确认。若之后改变接线或通道配置，需要重新核对这张映射表。

后续接官方深度算法，应统一上游眼别：当前`run_cam.sh`默认通道2/0，可在停止旧采集后改成：

```bash
source /opt/tros/humble/setup.bash
export ROS_DOMAIN_ID=0 ROS_LOCALHOST_ONLY=0
bash /opt/tros/humble/share/hobot_stereonet/script/run_cam.sh \
  --rotation 90.0 --channel 0 --channel2 2 --log_level INFO
```

这时先重新做遮挡确认；若上半幅已经是物理左眼，新算法入口就必须传`swap_eyes:=false`。**不要上游交换一次、下游再交换一次。** 测距用的标定参数、R/T和图像也必须对应同一眼别；仅靠遮挡通过，还不能证明深度数值准确。

早先集成测试记录：11项解码/配对单元测试通过，真实相机与BPU集成测试收到22帧检测结果，解码错误0；软件交换眼别已开启，深度保持无效。该轮检测结果接收频率约1.8fps，日志见`logs/mipi_vision_20261010/live_result.json`。这是历史测试记录。

早先三类原图网页验证：连续4次检查均为`live`、`detector_available=true`，更新帧不同；当时检测画面短时约1.36～2.27fps，JPEG为960×816，检测坐标对应1280×1088原图。这是**优化前的历史配置**。当前已改为火焰模式与640×544去畸变输出，不应继续引用旧数字作为本轮速度。YOLO已转为临时后台服务，请勿重复启动。

当前使用EEPROM来源的K/D和`R=I`做单眼去畸变，默认`lens_alpha=0.0`，参数文件为`config/gs130w_intrinsics_20261010.json`。这是候选参数画面矫正，眼别、实际投影和测距仍待实测核验。`/vision/frame.left`为640×544 BGR矫正图，`right`仍为1280×1088原始NV12，**不能直接把这对消息当作同尺寸双目整流图进行视差匹配**。详细切换和对照方法见[火焰模式与去畸变说明](火焰模式与去畸变_使用说明.md)。

与已有整车代码的关系：

- 旧`camera_node.py`仍用于其明确配置的V4L2横向SBS设备。当前MIPI链路使用新`mipi_camera_node.py`，不会再用OpenCV打开相机设备。
- `perception_node.py`复用现有BPU模型和YOLO后处理，从`/stereo/pair`接收图像。
- `mission_node.py`已有红绿灯状态机，但本次两节点入口不启动它。它在整车模式下收到FPGA斑马线事件后才进行相应搜索/灯态判断。
- `scene_node.py`已有OCR与场景关联，但还需要楼面ROI、任务状态等约束；检测到一个人不等于已经确认“3号楼有一个受困人员”。
- 当前二维识别不需要先完成双目标定；准确距离与灭火瞄准必须再验收眼别、曝光同步、标定、相机到喷嘴外参及落点。

```bash
bash tools/run_mipi_vision.sh swap_eyes:=false
```

## 8. 四个终端分别做什么，以及本次故障原因

### 当前运行方式：底层采集在终端，算法与检测网页由临时服务管理

底层相机和官方原图网页仍在用户终端前台运行，本轮没有重启它们。YOLO现在转入`rescue-mipi-vision`临时服务，8086单画面网页由`rescue-detection-preview`临时服务管理。早先曾使用的`rescue-mipi-camera`和`rescue-mipi-preview`并非当前运行方式；旧PID随重启改变，不应照抄用于停止进程。

**当前不要重复启动相机、YOLO或检测网页。** 原终端保留的旧报错不会自动消失，应看新图像和当前诊断判断。

在X5的root终端查看状态和日志：

```bash
systemctl status rescue-mipi-vision rescue-detection-preview --no-pager
journalctl -u rescue-mipi-vision -u rescue-detection-preview -n 60 --no-pager
```

仅当你确实需要停止它们时执行：

```bash
systemctl stop rescue-detection-preview
```

普通非root用户在上述`systemctl`命令前加`sudo`。上面的停止命令只关闭8086检测网页，不停止相机或YOLO。需要停止识别时执行`systemctl stop rescue-mipi-vision`，底层相机仍运行；关闭底层相机须在它的前台终端Ctrl+C。两项都是**当前开机期间的临时服务，未设置开机自启**。下一次开机按下方顺序手动启动即可，不要假定临时服务仍存在。

之前四个终端的职责如下，用于把采集、原图预览、识别、查看消息分开，方便学习和排错；不是必须打开四个VS Code窗口。现在8086网页已能可视化查看结果，原始消息终端可以按需使用。所有Linux命令都应在X5远程终端执行，不能输入电脑PowerShell。

| 终端 | 职责 | 正常状态 | 按Ctrl+C会怎样 |
|---|---|---|---|
| 1：官方相机 | 持续发布左右眼和合成原图 | 采集持续运行；终端暂时不刷新日志不等于停止 | 停止图像来源，其他视觉程序随后无新帧 |
| 2：网页预览 | 把现有合成图编码为JPEG并送到浏览器 | 网页出现连续变化的双目原图 | 停止这次预览，采集和YOLO可继续运行 |
| 3：视觉算法 | 左右图适配、交换眼别、运行YOLO | `/perception/detections`持续发布结果 | 停止这套识别，原始相机和预览可继续 |
| 4：查看结果 | `ros2 topic echo`读取识别消息 | 有目标时显示框，没目标时可能是空列表 | 只停止这次查看，不停止识别 |

### 历史诊断记录（不代表当前仍故障）

1. **ROS通信域不一致。** 实际检查时相机使用默认域`0`，网页编码和websocket进程使用域`71`。这就像在不同频道上收发：网页服务虽然启动，也收不到相机图像，所以提示几秒没有收到图。项目`env.sh`默认域为`71`，不能仅凭终端都在同一台板子上就认为它们能通信。本次MIPI相关程序统一使用`ROS_DOMAIN_ID=0`、`ROS_LOCALHOST_ONLY=0`。
2. **重复启动相机。** 已经执行`run_cam.sh`后，再执行官方`mipi_cam_dual_channel_websocket.launch.py`会额外尝试启动相机驱动，可能发生硬件占用或初始化失败。此时第一个采集进程可能仍正常，因此不能把第二个驱动的错误直接当成接线又坏了。网页改用下面的独立预览入口。
3. **旧驱动确实发生过停帧。** 旧相机进程PID32140仍存在时，日志出现约41～57秒的间断；后续一轮检查中，`left`仍更新，`right`和合成图的最近记录已经约149秒未更新，并持续出现`grab failed`。这会使双目配对和网页一起等待，不能归结为检测模型“没识别到目标”。已让旧进程通过SIGINT正常退出，再以相同图像/通道/触发参数、WARN日志级别和后台方式重新启动。**尚不能断言终端输出或INFO日志就是根因**；改为后台低日志量是排除干扰的措施，稳定性需看重启后的持续收帧结果。历史证据保留在板端`/root/.ros/log/mipi_cam_32140_1791625235977.log`。
4. **中途复测仍曾只有一眼。** 当时重启驱动未恢复，关闭LPWM的对照收到左话题797帧、右话题0帧、合成图0帧；整板重启后的另一轮右话题只收到30帧后停更。随后原LPWM配置恢复。如今双目已恢复并完成上述网页复测，但这些历史证据不足以单独确定排线或驱动哪一个是根因。

### 黄色提示和深度状态怎么理解

- **“环境已过时”之类黄色提示**是VS Code对终端环境变更的通知，不是相机驱动或YOLO抛出的错误。它通常表示扩展希望新终端采用更新后的环境；先看ROS进程和实际消息是否正常，不要仅凭这个图标重启所有程序。需要刷新时可在停止该终端自己的任务后新建终端，再按上述顺序加载环境。
- **`depth_valid: false`、`uncalibrated`或“未标定”**符合当前仅进行二维识别的配置：双目米制标定尚未验收，因此程序不输出可用于喷嘴瞄准的距离。检测类别和像素框仍可使用；不要把无效深度当真实零距离，也不要为了消除提示把`depth_valid`强行改成`true`。
- **`detections: []`**只表示当前帧没检出当前模式允许且达到阈值的目标。火焰模式请对准本项目壁纸中的火焰；消防员和人物不会输出，须先恢复三类模式再测试它们。普通房间画面不是这批训练数据的主要场景。
