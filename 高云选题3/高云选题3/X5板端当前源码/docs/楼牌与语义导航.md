# 楼牌识别、场景报告与语义导航

> 更新说明：本页讲解视觉/场景及旧 `/semantic/request` 符号解析接口。新语音/网页自动任务入口为 `/interaction/command`；实际道路规划、定位接口与执行门槛见[地图定位与导航](地图定位与导航.md)和[当前主README](../README_开始使用.md)。

现在新增的边缘 AI 模型是 **PP-OCRv4 轻量中文 OCR**，由 RapidOCR 1.4.4 调用 ONNX Runtime，在 X5 的 ARM64 **CPU** 上运行。三个 ONNX 文件约 16.2 MB：文字检测、文字识别、文字方向分类。现有 YOLO 仍用于火焰、普通人物、消防员检测。OCR 与 YOLO 的组合可以提供带证据的结构化场景报告；不需要先部署大语言模型才能读楼牌或统计当前画面中的目标。

## 程序怎样回答你的四个问题

先用 OCR 读取一楼楼牌。程序按当前地图的 13 栋楼名单精确匹配，保守地归一化全角数字、空白和标点，不把相似汉字或数字随意改写。`1号楼` 与 `11号楼` 是两个独立数字，不使用子串匹配。

同一楼牌需要最近 5 次观察中至少 3 次匹配，并且在同一画面区域保持空间一致。重复帧、过期帧不会凑够确认次数。一帧出现两个不同楼栋牌号时，整帧匹配会返回 `ambiguous`，应缩小已验证的单楼面观察区域后重新识别。

| 用户问题 | 当前程序输出 | 含义 |
|---|---|---|
| 现在多少号楼？ | `building_number`、`building_name`、`building_id` | 当前画面楼牌证据对应的楼，不是小车全球定位 |
| 是否有火灾？ | `fire_status=observed/not_observed/unknown` | 当前楼面发现火焰图案 / 本次未检出 / 证据不足；未检出不等于确定无火灾 |
| 几个人受难？ | `visible_person_count`，`casualty_count=null` | 只能统计当前画面普通人物目标，不能凭 person 类确定受困或伤亡 |
| 有无消防员？ | `visible_firefighter_count` | 当前画面消防员目标数，不能推断整栋楼的人数 |

你的训练数据是居民楼壁纸图案，故 `physical_fire_verified=false`。这些检测适用于地图任务演示，不构成对真实火灾的可靠确认。

为避免“甲楼牌 + 乙楼火焰”错配，`SceneMemory.observe()` 需要已确认的单楼面 ROI，并要求楼牌与检测结果来自同一帧、同一时间戳。ROI 应由人工安装调试或几何楼面关联确定；不能把整幅图简单标成已验证楼面。未提供时程序仍可报告楼牌，但楼内状态保持 `unknown`。ROI 的含义是当前可见楼面，不代表已观察整栋楼。

报告过期（纯核心默认 2 秒，当前 ROS 节点配置为 3 秒）后，当前火焰状态变成 `unknown`，人数变成 `null`。历史记录仍保留证据时间，不冒充当前观察。人数来自经过 NMS 的当前帧检测框，不把多帧人数累加。

## 接口与数据流

```text
同一双目左眼画面
 ├─ OCRReader.predict(BGR) → 文本、置信度、四边形
 │    └─ BuildingTracker.update() → 多帧确认的楼栋证据
 └─ YOLO → fire / person / firefighter 检测框
          ↓
 同帧、同一已验证楼面范围关联
          ↓
 SceneMemory.observe() → 场景报告 + 证据 + 有效期
          ↓
 任务管理器选择“继续观察 / 巡检某楼 / 寻找并瞄准火焰”
```

主要调用：

```python
reader = OCRReader('/path/to/rdkx5_ros2_ws/models/ocr', threads=2)
tracker = BuildingTracker('/path/to/rdkx5_ros2_ws/config/buildings.json')
scene = SceneMemory('/path/to/rdkx5_ros2_ws/config/buildings.json')

readings = reader.predict(left_bgr)
building = tracker.update(readings, stamp, frame_id)
report = scene.observe(
    building, detections, stamp, frame_id,
    facade_roi=[x1, y1, x2, y2], roi_verified=True,
)
```

其中 `detections` 是同一原始图像上的 `class_name`、`confidence`、`bbox`。异步 ROS 管线必须按帧编号/时间戳配对，不能简单取“最近一次 OCR”与“最近一次 YOLO”拼接。

## 怎样接语义导航

`scene.resolve_request('去 11 号楼观察', now)` 或 `scene.route_request('K', now)` 会输出：

```json
{
  "building_id": "K",
  "building_name": "绿荫楼",
  "intent": "inspect_building",
  "observation_point": {"id": "observe_K", "frame": "map"},
  "status": "symbolic_goal_only",
  "can_execute": false
}
```

这是语义目标接口。它接着要交给定位、道路拓扑规划、障碍物避让与阿克曼行驶控制。程序没有把它伪装成已完成的 Nav2 导航。当前观察点来自 `map_assets/rescue_maze_v6/config.json` 的真实地图数据，记录的是虚拟相机观察位置；尚未与实物场地坐标和车体坐标标定，不能直接当成车体导航终点。

支持的文本请求是显式楼号或完整楼名，不是任意自然语言理解。比如“去 1 号楼绿荫楼”有冲突，会拒绝自动挑选；“去最近没有消防员且有火的楼”这种组合语义，需要额外任务解析与充分场景证据。现阶段没有下载或部署 LLM/VLM，也不会把规则解析称为大模型推理。

## X5 依赖与性能安排

在 X5 对应 Python 环境安装 ARM64 版本的 `onnxruntime` 和 `rapidocr-onnxruntime==1.4.4`，并使用工作区提供的固定权重。桌面验证临时目录 `vendor/ocr_python` 含 Windows 依赖，不可直接拷到 ARM64 板运行；板端安装自己的依赖。

OCR 宜在停车观察或低频检查楼牌时执行，初始可设为每秒 1 次，在实板测量后调整；YOLO 和红绿灯控制采用独立更新节奏，不能让 OCR 阻塞停车与通信。这里没有宣称 X5 上的 OCR 帧率或 BPU 加速。

权重来源由 `models/ocr/manifest.json` 固定 URL、版本与 SHA256；上游 Apache-2.0 许可在 `vendor/ocr_source/`。`tools/prepare_ocr.py` 可重建模型目录。模型已下载，无需重新训练你的 YOLO。
