# 第二轮性能检查与优化

2026-10-11，在上一轮已部署优化的基础上，再检查真实 X5 的图像、网页和 ROS 任务控制路径。本轮仍保留相机及预览 1280×1088、YOLO 输入 640×640、JPEG 质量 90、三类识别模型、阈值、任务优先级和停车/喷水条件。

## 1. 已经修改并部署

| 修改 | 具体作用 | 保留的行为 |
|---|---|---|
| 网页连接启用 TCP_NODELAY | 避免小响应被 Nagle 与延迟 ACK 拖住，减少下一次取图前的等待 | 同一 JPEG 字节、同帧图像与检测框、过期判断、开关与租约 |
| UART 演练模式取消空读取定时器 | 没有串口对象时，不再每秒调用 50 次立即返回的函数 | 接真实 UART 时仍以 50 Hz 读取，STOP/权限心跳仍为 10 Hz |
| 任务模式取消闲置双目图像订阅 | 该模式原来的图像回调必定直接返回；现在不创建这个 reader | 道路/红绿灯观察接口、10 Hz 控制循环，以及旧模式的双目处理 |

三处生产代码分别是 `tools/detection_preview.py`、`src/rescue_vision/rescue_vision/fpga_bridge_node.py`、`src/rescue_vision/rescue_vision/mission_node.py`。没有更换模型或图像处理算法。

## 2. 实测结果如何理解

### 网页小响应：收益明确

在 X5 的独立 localhost 服务中，用同一预览处理器交替运行 A/B/A/B。每轮预热 5 次，再测量 40 次无新帧响应：

| 配置 | 两轮中位耗时 |
|---|---|
| 原先默认 socket 配置 | 49.97 / 49.93 ms |
| TCP_NODELAY | 3.88 / 4.04 ms |

四轮响应正文 SHA256 完全相同。测试使用临时服务，不修改在线任务，也不生成相机数据。它验证的是小响应等待减少约 46 ms，**不是 YOLO 推理快了 46 ms，也不是电脑浏览器的端到端画面延迟**。真实网络、图片大小和浏览器解码仍会影响显示效果。

证据：[HTTP 交替对照](../logs/performance_pass2_20261011/preview_http_abab.json)。复测工具：`tools/benchmark_preview_http.py`。

### 全栈：维持约 17 FPS，未证明再次显著提速

三类 YOLO、OCR 与网页传图同时运行，同一真实相机视野，前后各约 30 秒；测量时没有运行 profiler 或其他性能测试。

| 指标 | 本轮修改前 | 本轮修改后 |
|---|---:|---:|
| YOLO 处理帧率中位数 | 16.95 FPS | 17.20 FPS |
| 图像送达视觉节点 | 30.08 FPS | 30.01 FPS |
| 检测结果距采集时刻的时间 | 176.9 ms | 172.3 ms |
| 被测进程 CPU 合计 | 613.80% | 612.01% |

这些差异很小，短时间的调度、温度和 OCR 阶段变化都可能造成波动，**不能据此宣称获得稳定的额外 YOLO 加速或 CPU 降幅**。CPU 100% 表示占满一个核心；本工具的进程筛选不包含预览进程，数值不是全系统总占用。两次测量采用相同筛选。

证据：[本轮前测](../logs/performance_pass2_20261011/before_full.json)、[本轮后测](../logs/performance_pass2_20261011/after_full.json)。当前视野没有用于正式验收的打印目标，因此本轮没有重新给出实拍识别准确率。

## 3. 还可以往哪里优化

| 剩余环节 | 本轮观察 | 下一步需要的证据 |
|---|---|---|
| 全分辨率镜头校正 | 单阶段中位约 26–34 ms，受多线程和同时负载影响 | 新实现必须与原实现逐像素一致，且交替实测有稳定收益；上一轮 NEON 候选未达到这个条件 |
| JPEG 编码及发布 | 单阶段中位约 50–52 ms，与其他阶段并行，不能把它们直接相加计算 FPS | 当前已用 NEON + libjpeg-turbo；硬件编码或 FAST DCT 要另做图像质量/像素验收，不能默认等价 |
| BPU 调用与输出搬运 | forward 阶段约 32 ms，包含等待和传输 | 如继续修改，应先细分 BPU 等待、cache flush 和输出复制；不能直接跨帧共享可覆盖的输出缓冲 |
| ROS 执行器与节点通信 | 控制节点开销以执行器、消息收发为主，JSON 不是主因 | 可以评估 C++ 或受控的节点合并，但需验证故障隔离、并发、停止延迟和全部任务行为，属于更大的架构改造 |

当前 CPU 采样为 1.5 GHz，已达该板配置上限；BPU 约 996 MHz、内存控制器约 4266 MHz，也已接近配置上限。没有通过超频、降低分辨率、减少类别、改阈值或降低有效控制频率来获得数字提升。

原生采样只用于定位：第一次 99 Hz 采样给板端造成明显额外开销并报告落后，不能用它计算真实速度；之后改为 9 Hz、12 秒采样，无落后提示。低频样本很少且有未解析的原生符号，不能据此精确拆分 BPU 内部耗时。两份采样保留在记录目录中；上面的性能表来自不带采样器的独立测量。

## 4. 验证与使用

本轮板端 **51 项测试通过**，包括预览协议与 socket 设置、开关与过期行为、两种 UART 配置、两种任务配置，以及任务控制/执行器回归。新测试只在隔离 ROS 域 83 中运行，并用假的串口对象验证真实 UART 分支，没有操作实物串口、云台或水泵。

记录：[测试输出](../logs/performance_pass2_20261011/regression_tests.log)。构建后已重启预览和任务服务；相机、视觉、Qwen 继续使用原有配置。一次测试指令在任务服务刚重启、ROS 节点尚未就绪时返回“Task router unavailable”；节点就绪后同一指令成功，没有修改路由或控制逻辑掩盖启动状态。

完成后恢复初始的待机状态和传图开启。待机时 YOLO 按任务关闭，界面的帧率不能当作 YOLO 推理帧率。云台安装尚未验收，当前低头道路观察仍受姿态条件限制；真实执行器及 UART 仍为演练/禁用。

在 VS Code 的 X5 SSH 终端中开始观察：

```bash
cd /root/rescue/ros2_ws
export ROS_DOMAIN_ID=0 ROS_LOCALHOST_ONLY=0
source env.sh
python tools/task_command.py "寻找火焰"
```

结束观察：`python tools/task_command.py "任务结束"`。预览地址：<http://192.168.127.10:8086/>。网页 socket 设置已由服务重启生效，不需要安装新软件。
